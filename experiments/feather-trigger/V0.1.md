# Feather Trigger V0.1 — Feature Freeze

- Date: 2026-09-20
- Branch: development
- Status: Feature Freeze
- Implementation: `feather-trigger-v0.1.user.js`
- Phase 0 basis: `PHASE0.md`

## Purpose

Feather Trigger V0.1 adds a minimal external Context Freshness signal to ChatGPT conversations.

It does not store conversation content, project state, summaries, or Harness context.

It stores only the last detected user-send timestamp for each existing ChatGPT conversation and injects a lightweight signal into the next user message:

```text
[activity_gap: 14m]
<user message>
```

The AI remains responsible for deciding whether fresh Context or a Source of Truth must be reacquired. The timestamp is a signal, not the decision maker.

## Frozen V0.1 Scope

V0.1 implements:

1. Existing-chat conversation identification from the ChatGPT `/c/<conversation-id>` URL.
2. Per-conversation timestamp storage in browser `localStorage`.
3. Elapsed-time calculation from the previous detected user send.
4. Human-readable gap formatting:
   - seconds
   - minutes
   - hours/minutes
   - days/hours
5. Enter-send detection.
6. Send-button click detection.
7. Japanese IME composition Enter exclusion.
8. Duplicate detection suppression for closely related send events.
9. Composer injection of:
   `[activity_gap: ...]`
10. A small visible Feather status badge for V0.1 debugging/verification.

## Current Browser/UI Dependencies

V0.1 intentionally uses the currently observed ChatGPT Web UI rather than a larger compatibility layer.

Observed selectors/mechanisms:

- Composer: `#prompt-textarea`
- Send button: `button[data-testid="send-button"]`
- Enter: capture-phase `keydown`
- Injection: `document.execCommand('insertText', ...)`

These are implementation dependencies, not stable public APIs. A future ChatGPT UI change may require maintenance.

## Known Limitations

### New-chat bootstrap

A brand-new ChatGPT chat does not yet have a `/c/<conversation-id>` URL before its first message.

V0.1 does not add special bootstrap state for this case.

Current consequence:

1. First message in a new chat: no conversation ID, so no timestamp is stored.
2. Second user message: first timestamp is stored; no gap is injected.
3. Third user message onward: normal V0.1 gap injection is available.

This is accepted for V0.1 because the primary use case is detecting stale Context when returning to an existing conversation. It will be reconsidered only if real use shows meaningful value.

### Send-time semantics

The stored timestamp represents a detected user send action, not a confirmed server-side delivery acknowledgement.

If a send action is detected but the message later fails to deliver, the timestamp may still advance.

This is accepted for V0.1 and should be revisited only if it causes practical continuity errors.

### UI status badge

The visible badge is retained in V0.1 to make behavior observable during real-use validation. Hiding or redesigning it is cosmetic and intentionally deferred.

### Gap precision

Human-readable gap values are intentionally coarse after one minute. V0.1 does not need millisecond precision.

## Explicit Non-Goals

V0.1 does not:

- store message bodies
- store summaries
- store project names
- maintain a vector database
- maintain project IDs of its own
- decide when Context must be reloaded
- force Harness/GitHub reads
- create a fixed time threshold such as "18h means reload"
- modify Core/HARNESS rules automatically
- solve every new-chat or browser-lifecycle edge case

## Feature Freeze Decision

V0.1 is frozen at the smallest point where the core Feather loop works end to end:

```text
previous user-send timestamp
        ↓
elapsed time
        ↓
[activity_gap: ...]
        ↓
normal user message
        ↓
AI Context Freshness judgment
```

Further polish should be driven by real-use evidence rather than hypothetical completeness.
