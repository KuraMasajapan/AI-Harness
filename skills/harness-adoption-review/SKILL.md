# AI-Harnessの改善候補を選ぶ

試行ブランチで使う。候補の採否や試行範囲を判断する場面が対象。比較を伴わない日常の修正は通常の開発手順で扱う。

1. **目的と過去の判断を確認する。** 今回の不足と守るべき品質を明確にする。関連する提案原文、現行機能、[決定ログ](../../agents/Codex/DECISION_LOG.md)の該当項目だけを読む。既に調査済みなら結果を再利用し、新規の外部調査や出典の確認が必要なときは [research-dedup](../research-dedup/SKILL.md) に任せる。提案の二次評価は読む順番の目安として使う。
2. **目的が近い案を比べ、要素を選ぶ。** 現行方式も候補に入れ、埋められる不足、重複、証拠の強さ、維持と確認の負担を比べる。一案に絞る、補い合う要素を組み合わせる、独自の小案を作る、保留・見送りの中から選ぶ。複数を進めるときは、効果が見込める順に原則3件までを次の作業にする。
3. **小さく試す。** 変更前に、対象、現行との比較条件、守る品質、成功・中止条件、戻し方を決める。実装と実案件での効果確認を分け、欠測は未確認とする。品質や重要な文脈の保持が後退した候補は採用候補から外す。判定と権限の境界は [GOALS.md](../../agents/Codex/GOALS.md) に従う。
4. **結論を記録する。** 決定ログに、日付、適用範囲、比較候補、採否と理由、証跡、未確認事項、再検討条件を残す。後日結論を変える場合は旧IDを指す新しい記録を追記する。ポータルやカードを更新する場合は、同じ決定IDを参照する。試行の結果とHumanの正式採否は別々に記録する。

記録例は決定ログの **D-001**。固定ページと状態表示を部分的に取り入れ、作業編成・設定切り替えの機能は、対応すべき負担が生じた場合に再比較する。

長い資料を部分取得するときは、先に判断に必要な項目を列挙する。初回検索で拾えなかった項目は、同義語・英語名・状態名で追加検索し、判断に影響する項目が欠けたままなら該当する章か正本を読む。

## 継続を依頼されたとき

- [作業キュー](../../agents/Codex/IMPROVEMENT_QUEUE.md) を読み、現在の依頼・ブランチ・証拠と照合する。上から実行可能な項目を選び、実装と効果確認はそれぞれ未完の工程を進める。上位項目が待ちなら、その条件を記録して、依存しない次の項目へ進む。
- 1件ごとに比較・実行・検証を行い、結果と次の一手をキューに保存する。採否や理由が変わるときは決定ログに追記する。3件ごとに検証結果と残りの優先順を見直す。継続依頼の範囲内に次の作業があれば、区切りの報告後も同じ作業セッションで続ける。
- ユーザーの停止指示、利用上限、承認が必要な操作、重大な品質後退、または着手可能な項目がなくなったときは、その範囲の作業を止める。承認待ちと独立した作業は進めてよい。再開点と未確認事項をキューに残す。
