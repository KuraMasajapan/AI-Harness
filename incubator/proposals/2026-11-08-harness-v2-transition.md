# AI-Harness V2 — 移行条件と構成案

2026-11-08 JST。状態: 設計草案。現行Core・プロジェクト仕様・試行ブランチの採用状態を変更しない。
対象はHarness全体の次期構成であり、Codex出典評価v2やoffline preflight v3とは別の版を指す。

## 進み方

Codex試行で得た成果を、作業別に「実装できた」「現在の証拠を確認した」「実作業で効果を確認した」
「Humanが採用した」に分ける。検証が通った機構は設計の材料にできるが、性能改善や正式採用まで
推論しない。検証が弱い機構があっても構成比較は進められる。実行経路への組込みは別工程とする。

**設計を始める目処**: developmentの候補と重複を照合し、Codexの再開・検証・証拠保存の経路を
実ファイルと照合できること。試験状態・失効・未確認を区別でき、現行環境へ戻せること。

**限定試行を始める条件**: 新構成で差し替える部品を1つ選び、互換・失敗時の挙動・比較基準・
停止条件を先に固定する。現行の重要制約、必須検証、Human承認の全てを保つ。

**正式移行の条件**: 適用範囲で実作業比較が成立し、重大な品質後退がなく、計測した負担が改善する。
欠測の速度・token・品質は未確認のまま。既存証跡を保持し、rollback手順と残る差を示して
Humanが判断する。main統合・本番移行・公開・既存証跡削除を自動化しない。

## V2の6層と既存機構の扱い

既存の [6層参照アーキテクチャ](2026-09-21-ai-harness-reference-architecture.md) を骨格にする。
別のCoreやオーケストレータを新設する案とはしない。

| 層 | 保持・再利用するもの | 最初に検討する差分 |
|---|---|---|
| 1. Core | HARNESS / RULES / ACCESS、Humanの最終判断、正本、sealed境界 | 既存境界の実効性を確認。文書を読んだことと、操作を強制できることを区別 |
| 2. タスク・モード | 目的、重要制約、訂正、完了条件、次工程、版付きcheckpoint | 再開時の差分照合・再検証・再確認を判別する。Codexの試行出力を比較材料にする |
| 3. コンテキスト | 現行repoの原文、段階取得、明示選別した共有文脈 | Notionは背景と正本の案内。必要な情報のみ取得し、保護文脈は自動選別から外す |
| 4. 制御 | 既存の実行主体・承認経路、TRINITYの独立検証 | 利用枠・権限・失敗時経路を明示。モデル自動切替やhunch/Jev等の実行導入は保留 |
| 5. 実行 | Codexの試行ブランチ・既存CLI、Museの読取レビュー | agent固有機能と共有できる最小の入出力を分ける。全エージェント同時編集はしない |
| 6. 証拠・改善 | 既存gate、原文保存、既存receipt、固定された過去評価 | 状態表示は派生物。実usage・時間・人の訂正・再作業を別々に観測 |

## 最初の設計対象は3件

1. **再開境界:** 現行checkpointとsource/task/runtime照合をそのまま使う。次の操作を
   「差分を照合」「必要な検証を実行」「既存証拠を再確認」に分ける。
   読取表示に権限付与や自動再実行は持たせない。
2. **証拠の境界:** 既存検証・receipt・実体保存を再利用。古いPASS、入力欠落、承認待ちを
   区別し、TRINITYの既存規約・証跡を改変しない。表示や要約から逆に正本を作らない。
3. **共有文脈の境界:** NotionとHarnessの分担を維持。小規模な読み取り共有で保持と負担を
   確認する。Museによるレビューと、書込み許可・同時編集・自動同期の評価を分ける。

3件の評価に必要な情報は、既存成果物から参照する。新しいDB、全域スキーマ、常駐サービスは
今回の構成案で先に追加しない。必要性が実例で確認された段階で選択肢を比較する。

## 重要項目と確認先

着手時に必須条件を固定し、引き継ぎ時は次の3項目を正本に照合する。
不足・不一致・未確認があれば、その項目に必要な確認を明示してから先へ進む。
採否の比較と試行範囲は [決定ログのD-002](../../agents/Codex/DECISION_LOG.md#d-002-v2設計での重要項目の欠落対策) に記録する。

| 必須項目 | 何を照合するか | 不足・不一致の場合 |
|---|---|---|
| V2-01 再開 | 最新の依頼と、checkpointの目的・重要制約・訂正・次工程・参照版を照合する。既存の `begin` と `resume-plan` で確認先を特定する。 | 依頼と保存内容、ブランチまたは参照元が食い違う場合は差分を確認する。保存済みの指示だけで再開や再実行を決めない。 |
| V2-02 証拠 | 必須条件ごとに既存の検証結果・receipt・原文の所在を確認し、現行の `gate` と人の判断状態を確認する。 | 検証の欠落や失効は必要な再検証へ戻す。検証が通っても人の判断待ちはそのまま残す。 |
| V2-03 共有文脈 | 訂正や判断の背景は適用範囲・出典・確認日を確かめ、コード・仕様・採否はハーネスの正本に戻る。 | 正本に到達できない場合は未確認とする。共有メモに書かれた内容から権限や完了を推定しない。 |

限定試行では同じ入力・成果物・既存検証を使い、通常の引き継ぎと、この表を使う引き継ぎを比べる。
必須項目の抜け、確認や手直しの回数、所要時間を記録する。重大な見落とし、古い証跡の採用、
権限の取り違えが出た場合は試行を止め、既存の再開・検証手順へ戻す。

## 実行時制御レビュー

- **誰が保証するか:** 既存adapterのentry pointが参照元・runtime・証跡を照合する。
  AIの注意力に頼る操作を減らす。ネイティブの全操作を強制できるとは扱わない。
- **回避経路:** HTML・Notion・簡潔な再開表示だけで完了や公開を許可しない。
  必須検証とHuman判断は既存経路に残す。
- **継続性:** 目的・制約・訂正・次工程を既存の版付き記録に保存する。
  失効・不明・欠損時は復元や検証の必要性を表示し、古いPASSの再利用を止める。
- **負担:** 少量のローカル読取で済む場合は、外部サービスや再要約を追加しない。
  表示bytesと実token、単一CLI時間と総作業時間を区別して比較する。
- **戻す手順:** 候補の任意コマンドを使うのを止め、既存operation/gateへ戻る。
  現行ブランチ、元の試行結果、raw証拠、Coreを保持する。
