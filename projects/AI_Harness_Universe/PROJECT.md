# AI-Harness Universe — 宇宙型3D知識マップ構想

> **Status:** Concept preserved / Phase 0 — NOT IMPLEMENTED  
> **記録日:** 2026-10-21  
> **Repository:** `KuraMasajapan/AI-Harness` / `development`  
> **領域:** `projects/AI_Harness_Universe/`（JARVIS Soul UIとは**別プロジェクト**）  
> **出典:** ユーザーとAIの構想対話から生まれたアイデアを、後から再開できるよう整理した記録。以下は**設計の方向・例示・未決事項**であり、実装済みの機能や正式に固定したデータ構造ではない。

## 1. 構想の核 — 「AI-Harnessの宇宙地図」

GitHubリポジトリ **AI-Harness** の情報構造、知識の関係、情報の深さ、変化を、**探索できる3D宇宙**として可視化したい。

目指すのは「GitHubフォルダをそのまま宇宙に並べる」だけの3Dファイルブラウザではない。銀河、太陽系、惑星、衛星、生命のような構造が重なり、眺め、回し、近づき、離れるにつれて、関連する情報やその意味が見えてくる **知識の認知地図**。

- **中心から周辺へ**: 中核原則から周辺のプロジェクト・実験・記録へ。
- **ズームで深くなる**: 情報量を増やすだけでなく、見せる意味そのものを切り替える（**意味的ズーム / semantic zoom**）。
- **固定階層だけではない**: 一見無関係な情報の間にも、横断的な関連がある。
- **発見のためのUI**: クリックしてページを順番に開くより、空間を探索する途中で新しい組み合わせを見つける。
- **進化する地図**: 新情報、新しい参照関係、評価やプロジェクトの変化によって見え方も変わる。

### 発想を象徴する一言

**「宇宙には銀河と銀河の衝突もある。割と何でもあり」**。

銀河の衝突は単なるアニメーションではなく、**別々の知識領域の接近・交差・再解釈・新しい提案の誕生**を表すメタファーになり得る。実際に自動で情報を統合したり、Coreやルールを改変したりすることを意味しない。観測された関連性は「候補」、検証・採用は別の判断。

## 2. 宇宙メタファーによる5層モデル（初期の構想・仮置き）

| 探索段階 | メタファー | 情報の意味 | 見え方の例 |
|---|---|---|---|
| L1 | **銀河群・銀河** | 大分類・知識領域 | 遠景に発光する雲と大きな名称 |
| L2 | **太陽系** | サブシステム・機能群 | 中心星と機能グループ、他系との関係 |
| L3 | **惑星** | 主要コンポーネント | 個別機能と役割、周辺との結びつき |
| L4 | **衛星** | 補助機能・接続先・状態 | 関連スキル・ブランチ・機能・子構造 |
| L5 | **生命・植物・生態系** | 実際の知識・ルール・記録・提案内容 | 意味的な中身、文書、ルール、状態、証拠 |

これは固定的な存在論ではない。実データを調べたうえで階層の数や割り当ては調整可能。L5も文字どおりの生物を描かなければならないという意味ではない。生態系や成長のメタファーとして保留する。

### 最初に会話で出た銀河分類の例

- **クラウドAI銀河** — ChatGPT、Codex、Claude、Geminiなど
- **ローカルAI銀河** — Hermes、Ollama、Local LLMなど
- **記憶・知識銀河** — GitHub、Obsidian、倉庫番、（構想例としての）Airtableなど
- **実行・制御銀河** — Tools、Skills、MCP、Sandbox、Permissionsなど
- **研究・実験銀河** — Incubator、Proposal、Trinity、評価ログなど

別の表現例として **Core / Memory / Agent / Runtime / Research / Safety** の銀河構成も挙がった。**まだ単一の正式分類には決定していない**。

> 上記は視覚化の例であり、現在のGitHub上にそれらの名前のフォルダがあるという主張でも、全サービスが連携済みという意味でもない。Airtable等の現在の利用状況は将来の実データ同期時に確かめる。

### 太陽系以下の会話例

- **Memory銀河 → GitHub／Obsidian／倉庫番太陽系**。倉庫番の検索・索引コアを中心に、ローカルファイル、Markdown、GitHubノート、Vaultなどが関連するイメージ。
- **Agent銀河 → Hermes太陽系**。計画・Memory・Skills・Tool実行・Screen/Interfaceを主要惑星とするイメージ。
- **Control銀河 → Permissions太陽系**。Human approval・Guardrails・Policies・Access Scopeなどの関係を可視化。
- **Research銀河 → Proposal／Grok Reports／Trinity／Incubator太陽系**。
- **Skills惑星 → 衛星**。research-dedup・UI design・review・planning・debuggingなどの技能。
- **GitHub惑星 → 衛星**。main/development、incubator、projects、core docs等をどう見せるかの検討。
- **超近景の内容**。research-dedupなら一次評価、二次評価、重複検出ルール、保存境界。Proposalなら個別の検討項目や関連証拠・評価状態へ。

配置例は**説明のためのラフ案**であり、実ファイルの全容を調べて確定したマッピングではない。

## 3. 最も重要な設計原則 — 「階層」と「関係」は別

GitHubファイルパスは情報の**所在・所属（構造的な階層）**を示す。一方、同じ知識やアイデアは複数のテーマ・機能・プロジェクトをまたぐことがある。

例えばHermesというプロジェクトはAgentだけでなくMemory、Skills、Access、Runtimeにも関係する。一つの銀河へ押し込めて他の関係を消してはいけない。

そこで、将来の可視化は最低限2種類を分ける。

1. **構造エッジ**: ディレクトリ／文書の親子、定義済みの所属。
2. **関連エッジ**: Markdown参照、明示的な依存、共通概念、研究から見つかった関連**候補**。

関連エッジには根拠と確信度・検証状態が必要。**AIの類似性推定だけで事実の依存関係と断定しない**。複数銀河に関係する一つの実体は重複した「別物」にせず、同じIDへの複数の視覚的導線を設ける設計を検討する。

> **住所は階層、引力は関連性、銀河の衝突は新しい組み合わせの発見。**

## 4. 意味的ズーム / 探索インタラクション

| 距離 | 主に見せるもの | 主な行為 |
|---|---|---|
| 遠景 | 銀河、広い分布、主要な接続と光 | 宇宙全体の俯瞰、回転、近づく |
| 中景 | 太陽系、主要な中心、概要ラベル | 周囲を探索し、関係性をつかむ |
| 近景 | 惑星／衛星、役割、接続、状態 | 詳細へ進む、周辺を見渡す |
| 超近景 | ノート、Proposal、ルール、最終更新日、評価、参照元 | 必要なMarkdownやGitHub画面を開く |

**クリック依存を減らす**: 回転・パン・ズーム・ホバー・焦点移動を基本とし、詳細Markdownの表示、GitHubへの遷移、承認・実行などの明示的な操作でクリックを使う。

視界に全ラベルを常時出さず、距離・選択・必要度で表示を段階的に調整。大量ノードで「綺麗だが何も読めない宇宙」にならないよう、絞り込み・段階展開・必要な時だけ詳細読み込みを考える。2Dでの探索経路やアクセシビリティも将来検証する。

## 5. VFX・空間表現（あくまで参考、見た目未確定）

- 背景は深い宇宙、青〜紫の低照度。
- 銀河は淡い発光雲、太陽系は軌道や重力場の示唆、惑星／衛星は明瞭な情報ノード。
- 関係線は星間航路、神経、光の流れを連想させる。
- 状態例: **緑＝安定・採用、黄＝検討、赤＝保留・リスク、青＝研究、紫＝中核**。色は試案。種類・状態・重要度を色だけで混同させず、形状・ラベル・凡例とセットにする。
- 回転、接近、銀河の相互作用、粒子や光の変化は、情報の関係に結びつく時に価値がある。無意味な常時演出を優先しない。
- 3D Force-Directed Graphなどの空間グラフ技術と、WebGL / Three.js系VFXを将来比較できる。**今は技術選定・実装を開始しない。**
- 既存の**JARVIS Soul UIとは独立**。必要があれば共通のVFX技術や研究成果を参照するだけで、コードや設計を混ぜない。

## 6. 「銀河の衝突」「新しい星の誕生」の意味

宇宙のように、知識領域間の関係も変化し得る。

- 遠かったトピック同士に、信頼できる関連が見つかる → 星間の航路、接近、共鳴。
- 複数の提案・技術に、価値ある組み合わせが見つかる → 新しいProposalの候補、新星誕生の表現。
- プロジェクトが拡大・統合・廃止・アーカイブされる → 領域の成長・再編・過去の痕跡。
- 新しい関連が未検証 → 弱い光、仮線など、**確定情報と区別**して示す。

実際の天体物理を忠実にシミュレーションする必要はない。宇宙メタファーに自由度はあってよい。ただし**美的な重力表現とデータ由来の関連性を混同しない**。偶然近くに配置されたから関連がある、とはしない。

AIによる発見からCore変更やProposal統合を**自動実行しない**。検証・Human Reviewの境界を維持する。

## 7. ソース・オブ・トゥルースとデータモデル（将来の検討事項）

- 一次の事実はAI-HarnessのGitHub内容（リポジトリ構造、文書、リンク、明示されたメタデータ）。可視化は**派生ビュー**であり一次情報を勝手に書き換えない。
- GitHub実データの階層と、概念銀河のカテゴリの二重構造を扱う。
- 実装済み／研究中／構想／保留／アーカイブなどの状態を、推測ではなく根拠のある情報から表示する。欠損は「不明」。
- 同一文書のID、相互参照、変更履歴、出典リンクを保持する案を検討する。
- AIによる意味的関連提案は別レイヤーで管理し、根拠と承認フラグを持つ。
- 将来の実データ取り込み時には **core / projects / incubator / experiments / memory / skills / agents / evaluation** 等の実構造を確認し、実在しない概念ノードを実装済みとして表示しない。

## 8. 何に役立つか

- **俯瞰**: Harness全体を理解し、主要な知識群と分布を知る。
- **深掘り**: GitHubの何階層にも及ぶ情報を、位置を見失わずにたどる。
- **関係発見**: 別領域で繰り返される発想、共有できそうな機構、参照の抜けを探す。
- **保守と変化の観測**: 巨大化、孤立、更新、停滞、依存の集中を把握する。ただし判断根拠はデータに求める。
- **創発的な研究**: 一見無関係な提案が意味を持ってつながる瞬間を見つける。

見栄えだけでなく、**使えば理解が深まり、探索の中で発見が生まれる**ことを成功条件とする。

## 9. 将来の段階案（**すべて未着手**）

1. **Concept Definition**: この構想を失わず保存。どの宇宙階層がどの種類の情報に対応するかを仮定として整理。
2. **Repository Mapping**: AI-Harness実ディレクトリ・Markdown・リンク・概念を読み取り、仮の銀河／星系へ割り当てる。
3. **Read-only Prototype**: 最小の3D空間を回転・ズームし、階層を意味的ズームで展開。まずは少数のノード。
4. **Relationships**: 実参照エッジと意味的な候補エッジを区別して重ねる。根拠と出典を辿れるようにする。
5. **Evolution / Discovery**: 検証された変更履歴や関連性の発見を可視化。「銀河の衝突」表現の価値を検証。
6. **Performance & Usability**: 多数ノードの表示、モバイル、アクセシビリティ、2D代替、負荷と探索効率を実測。

これらは順序候補であり、実装を許可するものではない。

## 10. 境界・保全ルール

- **現在は構想保存だけ**。3Dエンジンの導入、アプリ作成、GitHubデータ収集基盤の実装は行わない。
- JARVIS Soul UIは別の目的・別の保存場所（`projects/JARVIS_Soul_UI/`）。このプロジェクトの作業でSOUL側を変更しない。
- `HARNESS.md`、`core/`、`memory/`、運用中の実験・各プロジェクトに副作用を出さない。
- 実装する場合も最初は**閲覧専用**。ファイル変更・AIエージェント実行・承認は明示的な権限分離を前提とする。
- この文書は**会話から生まれた思想と案の一次保存先**。確定仕様へ進める際は、ユーザーと現行リポジトリを再確認する。
