# Local AI Soul — V0.1 Product Specification

Status: FROZEN FOR IMPLEMENTATION  
Branch: development  
Purpose: Speed-first pilot implementation for a child-friendly local-first AI companion UI.

## 1. Product Goal

V0.1 must deliver one coherent experience:

- a dark, high-quality UI centered on an animated Orb,
- Japanese text conversation,
- optional local voice input/output,
- a first-run setup wizard,
- child-friendly language defaults,
- safe fallbacks when voice, reflex, or cloud AI fails.

The package distributes the structure, UI, orchestration, and setup flow. It does not provide or host permanent free AI service credits for users.

## 2. Supported Environment

V0.1 target:

- Windows 10 64-bit
- Windows 11 64-bit
- Chrome or Edge

Other operating systems and mobile are outside the V0.1 completion target.

Voice support is best-effort on supported Windows systems. If local voice requirements are not met, the application must still start in text mode.

## 3. Launch and Packaging

V0.1 uses a local web application, not a packaged desktop executable.

User-facing launch files:

- `setup.bat` — first-run setup
- `start.bat` — normal launch
- `stop.bat` — clean shutdown

Normal launch flow:

1. start local services
2. check service health
3. open the browser
4. load saved local settings
5. enter Ready state

The user should not need to enter command-line arguments, ports, model paths, or service commands during normal use.

## 4. Local-first Architecture

Default architecture:

```text
Browser UI
   |
Local Node Server
   |-- local settings
   |-- API credential protection
   |-- provider orchestration
   |-- health checks
   |
   |-- Sarashina API
   |
   \-- speech.cpp
```

Principle:

**Local-first / Cloud-optional**

The V0.1 recommended conversation service is Sarashina API, while provider roles must remain replaceable.

API credentials must not be stored in browser localStorage or exposed to browser-side code.

## 5. Recommended AI Roles

At V0.1 freeze time, the recommended Sarashina configuration is:

- `sarashina3-mini` — main Japanese conversation
- `sarashina3-nano` — Semantic Reflex / structured UI-state classification
- `sarashina3-guard` — safety classification

Sarashina is recommended because its API is currently suitable for a low-cost pilot. The UI and documentation must state that free availability may change and is not guaranteed permanently.

Provider interfaces must remain replaceable so future adapters can use other cloud APIs, OmniRoute, Jev, Sokudan, or local models without redesigning the whole application.

## 6. Semantic Reflex

The Orb must not depend on a large reasoning model for basic motion.

### Deterministic base states

The application code controls states that can be directly observed:

- Ready
- Listening
- Processing / Thinking
- Speaking
- Attention / Error

Examples:

- microphone active -> Listening
- LLM request active -> Processing
- TTS playback active -> Speaking

These states do not require model inference.

### Semantic layer

The Semantic Reflex may add limited nuance using structured output such as:

```json
{
  "tone": "caution",
  "energy": 0.55,
  "focus": 0.80
}
```

Recommended bounded values:

- `tone`: normal | focused | caution | alert | success
- `energy`: 0.0-1.0
- `focus`: 0.0-1.0

The renderer maps those values into approved presets and ranges.

The model must not freely control arbitrary rendering values.

Required safeguards:

- clamp numeric values
- validate structured output
- smooth rapid changes by interpolation
- ignore invalid output
- keep deterministic state active if Semantic Reflex fails
- preserve the previous safe state on timeout

## 7. Orb Renderer

V0.1 adopts the external OSS package:

- package: `jarvis-ai-web-animation`
- verified package version at design freeze: `0.1.2`
- upstream: `cyber1443/jarvis-ai-orb-web-animation`
- license: MIT

### V0.1 policy

Use the Orb's existing visual design substantially as provided.

Allowed adjustments:

- palette
- existing state selection
- custom state target using already exposed properties
- intensity
- energy-related mapping
- rotation speed
- particle speed
- shell radius
- ring spread
- filament opacity
- core scale
- bloom
- quality setting
- layout integration

Do not add in V0.1:

- new shaders
- new particle systems
- new movement primitives
- lightning/ripple systems
- major renderer source rewrites
- custom visual effects that require modifying the renderer architecture

The goal is integration, not renderer redevelopment.

### Branding boundary

The distributed product must not use JARVIS as its default assistant identity or imply Marvel/Iron Man affiliation.

The user chooses the assistant's display name during first-run setup.

The existing repository directory name `JARVIS_Soul_UI` is retained as a legacy internal project path for speed and continuity; it is not the final public product name.

## 8. Visual Design

V0.1 visual direction:

- background: black to very dark navy
- Orb: primary visual focus, centered slightly above the vertical midpoint
- response text: placed so it does not visually compete with the Orb
- text appearance: softly luminous white / blue-white rather than flat pure white
- minimal chrome and minimal permanent HUD

Suggested text roles:

- main response: pale blue-white
- secondary/system text: dim blue-gray
- caution: amber/yellow
- alert: soft red

Text should appear as the assistant's voice in the scene rather than as a conventional chat bubble.

### Text style presets

Provide three user-selectable presets:

- Cinematic — strongest atmosphere, softer contrast/glow
- Balanced — default
- Clear — higher contrast, reduced glow

V0.1 should use existing CSS effects only. Do not create a separate complex text-rendering engine.

## 9. Child-friendly Language

V0.1 includes a user-selectable language difficulty setting.

Recommended presets:

- Easy — more hiragana, shorter and simpler wording
- Elementary Standard — approximately understandable through elementary-school level, with difficult terms explained simply
- Original — normal model output style

Default:

**Elementary Standard**

For V0.1, this is implemented primarily through model instructions.

Do not build a full kanji dictionary, compulsory character-conversion engine, or perfect grade-level validator in V0.1.

The system should prefer simple vocabulary as well as simpler kanji. Kanji restriction alone is not sufficient.

## 10. Voice Runtime

Preferred V0.1 local voice runtime:

- `speech.cpp`
- VAD: Silero VAD
- STT: Parakeet Japanese candidate for short conversational speech
- TTS: Qwen3-TTS 0.6B

The exact downloadable model/runtime compatibility must be checked during implementation and setup.

### User-facing voice setup

The user should see only two essential steps:

1. choose a voice
2. test the microphone

Behind the UI, setup handles:

- speech.cpp availability
- required model availability/download
- service startup
- health checks
- microphone permission guidance
- error handling

If voice setup fails:

- explain that voice can be configured later
- continue setup
- start the product in text mode

Voice failure must not block Sarashina + Orb + Text operation.

## 11. First-run Setup Wizard

The entire first setup should feel like one guided experience, not a collection of technical configuration pages.

Recommended flow:

1. environment check
2. Sarashina API setup
3. connection test
4. choose the assistant's name
5. choose/test voice
6. microphone test
7. choose language difficulty
8. choose Text Style
9. completion / first greeting

Technical details should be hidden unless the user explicitly opens an advanced section.

The setup may separate parent/admin technical tasks from child-facing personalization, while remaining within one coherent wizard.

The assistant has no default public character name. The name chosen by the user is stored locally and used throughout the UI.

## 12. Local Settings and Privacy

V0.1 stores locally:

- assistant display name
- selected voice
- language difficulty
- Text Style
- Orb/UI preferences required for normal operation
- setup completion state

API keys are stored only on the local server side in an appropriate local secret/config mechanism and are never exposed to browser storage.

V0.1 does not persist conversation history.

V0.1 does not add telemetry or analytics.

Long-term memory, cloud sync, user accounts, and cloud databases are outside scope.

## 13. Safety

V0.1 uses layered safety:

- Sarashina Guard for input/output classification
- fixed application rules
- safe fallback responses
- bounded Semantic Reflex outputs

Guard output is not treated as a guarantee of child safety.

For child use, unsafe or uncertain output must fail toward a safe, short response instead of being spoken automatically.

TTS should begin only after the output has passed the V0.1 output-safety step.

## 14. Failure Behavior

### Sarashina unavailable

- show Attention state
- show a short local error message
- do not crash the UI

### Semantic Reflex unavailable

- continue conversation
- continue deterministic Orb states
- use safe/default visual state

### speech.cpp unavailable

- continue in text mode
- allow voice setup to be retried later

### WebGL/renderer limitation

- use the upstream component's supported quality/fallback behavior where possible
- never make renderer failure destroy the text interaction path

### Invalid local settings

- fall back to safe defaults
- offer setup repair/reset

## 15. Explicit V0.1 Exclusions

Do not implement in V0.1:

- wake word
- barge-in
- long-term memory
- RAG
- web search
- MCP/plugins
- PC control
- smart-home control
- scheduled autonomous tasks
- file upload
- voice cloning
- Jev adapter
- Sokudan adapter
- OmniRoute-specific integration/UI
- cloud database
- user accounts
- telemetry
- multiple personalities
- autonomous agent features
- renderer redevelopment
- desktop EXE packaging
- macOS/Linux/mobile completion targets

Interfaces may be kept replaceable where useful, but excluded features must not delay V0.1.

## 16. Definition of Done

V0.1 is complete when the following flow works on the supported pilot environment:

```text
setup.bat
  -> environment check
  -> setup wizard
  -> Sarashina configured
  -> assistant named
  -> voice attempted/configured
  -> preferences saved
  -> setup complete

start.bat
  -> local services start
  -> browser opens
  -> Ready

user speaks or types
  -> input acquired
  -> safety check
  -> Sarashina conversation response
  -> response text displayed
  -> Semantic Reflex updates permitted Orb characteristics
  -> output safety check
  -> TTS plays when available
  -> return to Ready
```

Also required:

- typed chat works without speech.cpp
- Semantic Reflex failure does not stop chat
- voice failure does not stop text interaction
- API failure does not crash the UI
- API key is not exposed to browser storage
- conversation history is not written to disk
- Windows 10 and Windows 11 are both included in the V0.1 support target
- Orb appearance remains close to the adopted OSS implementation
- user can change text readability settings

## 17. Third-party / Release Gate

Before public distribution:

- preserve the MIT copyright and permission notice for `jarvis-ai-web-animation`
- create or update third-party notices
- review licenses for speech.cpp and all distributed/downloaded model weights
- distinguish engine license from model-weight license
- avoid public branding that implies affiliation with existing fictional IP
- re-check current Sarashina terms, pricing/free availability, and usage requirements

This specification freezes the implementation direction, not permanent external-service availability.
