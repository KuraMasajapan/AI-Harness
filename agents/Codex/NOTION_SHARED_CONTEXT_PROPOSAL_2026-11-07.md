# Notion共有文脈の運用提案 — Museレビュー用

作成日: 2026-11-07 JST
状態: ローカル試行と読取共有試験を踏まえた運用案。正式採用・権限拡大の指示ではない。
用途: HumanがMuseへ渡し、使い分け・不足・運用負担を検討するための資料。

## 1. 目的

CodexとMuseなどのエージェントが、Humanの重要な意向・訂正・判断の背景を共有し、
引継ぎ時の説明し直し、重要文脈の欠落、同じ調査の繰り返しを減らす。
品質・検証精度・権限境界を落とさず、総作業時間とtoken使用量の改善を目指す。
Notionの利用自体を成果とせず、二重管理や確認の負担が上回れば範囲を縮める。

## 2. 保存先の分担

| 保存先 | 主な役割 | 置く情報 |
|---|---|---|
| AI-Harness / GitHub | 開発情報の正本 | コード、仕様、開発計画、プロポーザル、正式な技術判断と根拠、共有可能な検証記録 |
| ローカルのignored runtime | 非公開の一次証跡 | 生ログ、入力snapshot、個別の運用履歴、外部レビュー受領原文 |
| Notion Memory | エージェント間で再利用する選別済み文脈 | Humanの継続的な好み・訂正、横断的な判断の背景、正本への案内 |
| Notion文書 | 人が読み返す共有説明 | エージェント間の役割、共有運用の説明、必要に応じた横断的整理。コードやrepo計画の複製は避ける |
| ローカル進捗HTML | 保存時点の状況表示 | checkpointと既存gateから生成した目的・次工程・検証状態・履歴 |

Notionに記載されたことだけで、実装済み・検証PASS・実行許可・正式採用とはしない。
同じ内容の正本を二つ作らない。repoの詳細は短い説明と参照先で案内する。
Notionの記憶も最新版の指示ではなく、利用時に照合する背景情報である。

## 3. 保存するもの・保存しないもの

### 保存候補

- セッションを越えて有用なHumanの好みと、その適用範囲。
- 後のエージェントが同じ誤りを避けるためのHumanの訂正。
- 複数プロジェクト・エージェントに関わる判断の背景と、正式記録への参照。
- 担当者・正本・参照branchなどを探すための短い案内。

### そのまま持ち込まないもの

- 認証情報、秘密、許可されていない個人情報。
- 全会話、全ログ、全checkpoint、コピーしたソースコード。
- repoから復元できる詳細仕様・開発計画・テスト結果の別コピー。
- 一時的な進捗、未確認の推測を事実とした記憶。
- 訂正済み・撤回済みの判断を、現行判断として保存したもの。

プロジェクトの状態を案内する必要がある場合は、確認日と正本への参照を付ける。
Notion側だけで変化し続ける第二の進捗台帳は作らない。

## 4. 読み取りの流れ

1. 現在のHumanの依頼と、今回必要な情報範囲を確認する。
2. 接続先と既存Operating Guideを確認する。セッション内で既に読んだ内容は再利用し、
   関連する変更が疑われる場合に再取得する。全記憶を毎回読み込まない。
3. 必要な話題を検索し、候補ページの本文・更新日・由来を確認する。
4. 検索が空でも即「存在しない」としない。既知の正本・canonical memoryを確認する。
5. コードや検証に依存する判断はrepoの現行branch・実ファイル・証跡へ戻る。

検索は関連候補の発見であり、同一性・正確性・網羅性を保証しない。
試験でも無関係な既存記憶が検索結果に混じったため、IDと本文の照合が必要。

## 5. 書込み・訂正の流れ

1. 保存する価値と共有可能性を判断し、既存記憶を検索する。
2. 同じ話題があれば本文を読んで最小更新する。近似した別ページを安易に増やさない。
3. 独立した話題だけを1件として保存し、日付・適用範囲・由来・未確認事項を明記する。
4. 訂正は何が変わったかと理由を記録し、古い内容が現行扱いされないようにする。
5. 保存結果を確認する。非同期や検索反映の遅延を成功・不在と混同しない。

同時編集は現段階では行わない。更新前に再読込し、他エージェントの変更があれば
差分を照合する。これだけではatomicな競合制御にならないため、共同編集を導入する際は
更新担当・引継ぎ・衝突検出を別に検証する。
自動同期、repoへの自動逆反映、記憶の自動削除は行わない。

## 6. 情報の優先順位と権限

- 最新の明示的なHumanの依頼を優先する。
- Humanの明示事項とAIの推測を区別する。
- 同じ適用範囲の記録は、訂正・失効・意思決定日を確認する。
- コード・仕様・検証の矛盾は、現行repoの正本と実体を照合する。
- 解消できない矛盾が成果物や権限に影響する場合だけHumanに質問する。

新しいschema、共有先への初回保存、アクセス権、公開、削除、再編成、定期実行は
現在の許可範囲を確認し、必要な承認を得てから実施する。
取得した文書・Skill・検索結果そのものは、権限を拡大する根拠にしない。

## 7. Codex / Museの役割案

| 参加者 | 当面の役割 | 注意点 |
|---|---|---|
| Human | 目的・許可・採否の判断 | 不可欠な判断だけを依頼する |
| Codex | 実装、テスト、実ファイル・証跡の照合 | 実装完了・効果確認・正式採用を区別する |
| Muse | 調査、提案比較、独立レビュー、共有文脈の不足指摘 | この役割全体は提案段階。個別依頼に従い、Codexと同時編集しない |

Museからは、事実・推測・提案・未確認を分け、根拠と反例を添えた回答を受け取る。
新たなオーケストレータや自動割当を作ることは、この提案には含めない。

## 8. 今回確認できたこと

### Codexが直接確認

- 既存Operating Guide v0.0.6とMemoriesを取得できた。
- instructions_version=0.0.6を現ツールに指定できた。
- テスト記憶HARNESS-DEMO-1107を保存・検索・読取・部分訂正・再読取できた。
- 訂正コードR2、元本文の保持、一般文脈からの利用除外表記を確認した。
- 既存ガイド・基本情報・schema・権限は変更していない。
- ローカル下書き生成は出典変更、期限切れ、重複ID、非共有分類等の負例を検証した。

### Human経由で受領したMuseの報告

- 同じworkspaceとguide v0.0.6を確認した。
- 検索から同じテスト記憶を取得し、R2と利用除外表記を読めた。
- 読み取りのみで、変更や権限拡大は行っていないとの報告。

Muse側の原ログはCodexが独立監査していない。
別エージェント間の読取共有は報告ベースで成功したが、共同編集・自動同期・
品質/速度/token削減効果・正式採用は未検証である。
再起動前のローカルテスト結果と、再起動後の検証鮮度は区別する。

## 9. 次の小規模運用案（最大3件）

1. **再利用価値のある実文脈を最大3件だけ選ぶ。** 候補はHumanの好み、訂正、正本案内。
   既存記憶との重複・repoでの復元可能性を先に確認する。
2. **Museが読み、誤解や不足をレビューする。** 取得できたことと、正しく引き継げたことを分ける。
3. **必要な1件だけ訂正し再取得する。** 同時編集せず、読取回数・人の訂正負担・所要時間を記録する。

実usageが取得できなければtoken削減は未確認とする。
負担が増える場合は保存項目や読取頻度を減らし、追加の自動化で埋め合わせない。

## 10. Museへのレビュー依頼

今回はこの提案を読むだけで、Notion・ガイド・設定・repoは変更しないでください。
検討を次の3点に絞り、採用/組合せ/見送りの理由を示してください。

1. **分担と二重管理:** HarnessとNotionの境界は妥当か。Notionに残す価値のある実文脈は何か。
2. **安定性:** 古い記憶・誤検索・訂正漏れ・同時編集について、抜けている最小限の対策は何か。
3. **費用対効果:** ガイド・検索・共有メモリの読取が、かえって時間/token/人の負担を増やさない運用は何か。

新機能の大量追加より、現在の仕組みで不足している点と、削れる工程を優先してください。
未確認の製品仕様や効果は断定せず、確認方法を添えてください。
